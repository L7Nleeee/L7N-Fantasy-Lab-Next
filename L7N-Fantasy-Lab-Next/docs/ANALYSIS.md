# 產品理解、原版問題與設計決定

## 1. 從原始碼理解到的產品目標
L7N 想解決的是 **H2H Category Fantasy 的三個連續決策**：
1. **選人（Draft / 補強）**：用「參考池」把每位球員在 13 個分類的表現換算成 Z 分數，彙整成球隊的分類強弱，再用 Base Fit / Team Fit 回答「現在最該補哪裡、誰最適合」。
2. **每週對戰（Weekly H2H）**：球員每場平均 × 該週賽程場次，逐項預測我方與對手的 13 個分類勝負，並整理策略。
3. **看清外部參考**：Yahoo 預選順位、2026 新秀、NBA 賽程只是輔助，**不得改變核心引擎**。

核心規則（已原樣保留並用原版程式碼驗證）：50 為中性；參考池＝GP ≥ 最低 GP 且 ≥ 12 MPG（新秀需有 NBA 實績）；前 200 名或合格球員池；5%/95% winsorized 的平均與標準差；Z 截斷 ±2.5；
FG%/FT%/3P% 以「（命中率 − 池平均）× 出手數」量化且只用上季 GP ≥ 20 的球員建池；TOV 為反向；DD 以 DD/G 計分、TD 不計分；A/T = 總 AST ÷ 總 TOV；
球隊強弱 = Σz/√n → 50 + 20·tanh(z/2.5)；Team Fit 對弱項加權（最高 ×2.5）、對強項降權（最低 ×0.55）；週預測以總命中÷總出手計算百分比。

## 2. 在原始碼中發現的主要問題（含證據）
| # | 問題（V4.0.21） | 風險 | 新版做法 |
|---|---|---|---|
| 1 | 完整 2025-26 資料**不在 ZIP 內**，啟動時才由遠端 CSV 載入（8 秒逾時）；失敗就退回只有 11 人的 `demo()`，而 demo 沒有分鐘數 → 參考池為空 → 所有 Z 分數變成不可靠的 ±2.5 | 離線時看起來「算成功」但數字是垃圾 | 參考池 < 30 人時引擎明確回報「不可用」，UI 顯示橫幅並隱藏 Fit，不假裝計算 |

## 3. 刻意的偏離（均不影響核心計算結果）
- **Team override 不再寫進球員資料**，而是執行期由快照疊加（更新快照不必重新匯入）。
- **TOV 排序**：候選／球員表以「失誤由少到多」排序（原版 TOV 與其他項目一樣由大到小）。排序不影響任何分數。
- **DD / TD 欄位**：CSV 有 `dd`/`td` 欄位時使用該欄位；沒有才用內建 2025-26 對照表（原版永遠只用對照表，因此只有約 29 人有 DD）。
- **「接近」標籤**：相差 < 3% 的分類顯示提示，**僅 UI**，勝負判定仍是原版的嚴格比較。
- **What-if** 額外顯示分類強弱前後變化（沿用同一個強弱公式）。
- **參考池防呆**：參考池 < 30 人時不輸出分數（原版不會，見上表 #1）。

## 4. 技術取捨
- **原生 ES Modules、零依賴、無建置也能跑**。沙盒沒有 npm 網路，React/Vite 的建置結果我無法實際驗證；零依賴也讓使用者「雙擊 / 重新整理」就能跑、部署只是複製檔案。引擎是純函式，之後要換成 React 也只需要重寫 `src/features/`。
- **渲染**：字串模板 + 事件委派，輸入框不在重繪區內（不會失焦）；每個區塊以輸入簽章 memo；表格先顯示 40–50 列，其餘「顯示更多」。
- **儲存**：localStorage 單一命名空間；寫入失敗會顯示在畫面，不吞錯。
- **單檔版**：`scripts/build.mjs` 內建的小型打包器，把 40 個模組、CSS、Logo 內嵌為一個 HTML，可 `file://` 直接開啟。

## 5. 已知限制
- 沒有真實球季資料可用於本次測試（沙盒無外網）：遠端 CSV 欄位格式依原版程式碼的解析規則推定；實際 CSV 若欄位別名不同，請在「資料中心」看錯誤訊息或回報。
- 球員照片依賴 Wikipedia 名稱對應：同名或頁面沒有照片的球員會顯示首字母頭像。
- 賽程是原版內建的 2026-27 快照（每隊 80 場，官方 80/82）；沒有即時交易來源，季中交易需手動覆寫。
- Yahoo 名單、新秀 NCAA 數據沿用原版內建資料（核對日 2026-09-23 / 2026 選秀），沒有重新查證。
